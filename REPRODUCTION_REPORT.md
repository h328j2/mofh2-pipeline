# Reproduction Report

## Purpose

This report is the durable runbook for reproducing the MOF hydrogen-storage
screening and transfer-learning work in this repository. It records the data
sources, directory layout, simulation conventions, model stages, exact commands,
expected outputs, validation checks, and recovery procedures.

The central prediction target is volumetric hydrogen uptake in g/L. The DOE-style
deliverable swing is:

```text
DOE swing = uptake(77 K, 100 bar) - uptake(160 K, 5 bar)
```

The reusable transfer checkpoint is:

```text
model_repo/models/finetune_160_finetuneW_ensemble.pth
```

It predicts absolute uptake at 160 K / 5 bar using structural GNN features plus
160 K Widom features.

---

## 1. Repositories and provenance

The work combines two projects:

| Project | Role |
|---|---|
| `ML-Screening-of-Metal-Organic-Frameworks-for-Hydrogen-Storage-material` | hMOF pretraining, baseline GNN checkpoints, baseline screening analysis |
| `mofh2-pipeline` | RASPA validation, CoRE-2019 transfer learning, DOE-temperature modeling, screening |

The hMOF project supplies the pretrained 77 K model ensemble. The pipeline
repository supplies the real-MOF data, RASPA configurations, transfer scripts,
and final checkpoint.

The pipeline should be treated as the authoritative reproduction repository.
The hMOF repository remains necessary if the original pretraining notebooks or
data-analysis notebooks must be rerun.

## 2. Dataset lineage

### 2.1 hMOF preliminary/pretraining dataset

The baseline models were trained on approximately 137,953 hypothetical MOFs from
the MOFDB/Bobbitt-Snurr release. The labels are simulated H2 uptake at:

- 77 K / 2 bar;
- 77 K / 100 bar;
- deliverable capacity `100 bar - 2 bar`.

The baseline target is volumetric uptake in g/L. The model inputs include:

- framework graph and local atomic features;
- density;
- void fraction;
- surface area;
- largest cavity diameter (LCD);
- pore-limiting diameter (PLD);
- surface-area-per-volume descriptors.

The pretrained random-seed checkpoints used by the transfer scripts are:

```text
model_repo/models/gnn_full_random_s42.pth
model_repo/results/gnn_full_random_s43.pth
model_repo/results/gnn_full_random_s44.pth
model_repo/models/gnn_full_random_s45.pth
```

These are 77 K hMOF models. They must not be interpreted as direct 160 K DOE
models.

### 2.2 CoRE-2019 real-MOF dataset

The real-MOF transfer dataset is selected from CoRE MOF 2019. The packaged
selection tables preserve the original experiment:

```text
data/core_meta.csv       12,023 structure metadata rows
data/core_res.csv        fast pore-size results
data/core_stageA.csv    1,000 Widom-selected candidates
data/core_stageB.csv      500 final CoRE candidates
```

`core_stageB.csv` contains:

- 425 CoRE-2019 training structures;
- 75 held-out CoRE-2019 test structures;
- `kH`, `qst0`, `logkH`, and split metadata;
- a 30-MOF subset marked for 77 K / 100 bar validation.

The transfer training also uses 58 real-library MOFs from `real_picks.csv`.
Eleven external CoRE/hMOF structures are used only for external evaluation.

### 2.3 Simulation-derived labels

The 160 K transfer target is generated by RASPA:

```text
160 K Widom insertion  -> kH and qst0
160 K / 5 bar GCMC     -> supervised uptake target
77 K / 100 bar GCMC    -> DOE validation for the held-out subset
```

The corresponding queue manifests are:

```text
data/q_w160.txt
data/q_stage2.txt
data/q_g160_known.txt
data/q_stage3.txt
```

The raw original outputs are packaged in:

```text
reference/reference_runs.tgz
```

This archive contains the reference RASPA outputs needed to reproduce the saved
CSV results without rerunning every simulation.

## 5. RASPA convention

The standard production force field is `UFF_FHm2`:

- UFF framework Lennard-Jones parameters;
- single-site H2;
- `epsilon/k = 36.7 K` for H2-H2;
- `sigma = 2.958 A`;
- Feynman-Hibbs correction;
- H2 mass `2.016 u`;
- no electrostatic charges;
- 12.8 A van der Waals cutoff;
- replicated cells selected for the cutoff.

Do not silently substitute another force field when reproducing labels. The
repository also includes `UFF_FH` and `UFF_noFHH2`, but those are alternate
conventions used for comparison.

The parser converts the raw RASPA loading to the project's volumetric g/L
convention using the framework density:

```text
uptake_gL = raw_loading * framework_density_kg_per_m3 / 1000
```

GCMC is stochastic. Independent runs should be compared using block errors and
relative differences, not exact text equality.

```bash

python "$WORK/build_queues.py"
```

## 7. First validation simulation

Before any long run, validate one known CoRE structure. The following example
uses `C19_BADJIC_clean` at the DOE discharge condition:

```bash
mkdir -p "$WORK/verify_C19_BADJIC_160_5"
TEMP=160 \
FF=UFF_FHm2 \
WORK="$WORK" \
bash src/run_fh.sh \
  C19_BADJIC_clean \
  5 \
  1000 \
  1000 \

  "$WORK/verify_C19_BADJIC_160_5"
```

```bash
grep -q "Simulation finished" \
  "$WORK/verify_C19_BADJIC_160_5"/Output/System_0/*.data
```

The output should be under:

```text
$WORK/verify_C19_BADJIC_160_5/Output/System_0/*.data
```

1,000-cycle reruns produced approximately 2.432 and 2.596 g/L, demonstrating

## 9. Generating feature caches

The model scripts do not featurize every structure inline. They read pickle
caches containing graph tensors and global descriptors.

Create the cache directories first:

```bash
mkdir -p "$WORK/core_cache" "$WORK/real_cache" "$WORK/screen_cache"
```

Generate CoRE features:

```bash
cd "$WORK"
python featurise_core.py
```

This creates one file per CoRE structure:

```text
$WORK/core_cache/<raspa_name>.pkl
```

Generate real-library features:

```bash
python featurise_real.py
```

This creates:

```text
$WORK/real_cache/<library_name>.pkl
```

Zeo++ is the main bottleneck. Completed pickle files are reusable. If a job is
interrupted, rerun the command; existing files are skipped where supported.
For large runs, use multiple workers only when memory is sufficient.

Each successful feature record should contain:

```text
x
edges
dists
void_fraction
surface_area_m2g
surface_area_m2cm3
lcd
pld
density
elements
status = "ok"
```

## 10. Reproducing the 160 K transfer model

After feature caches and reference outputs exist:

```bash
cd "$WORK"
python train_160.py
```

The script loads:

- 4 pretrained 77 K random-seed GNNs;
- 423 usable CoRE training rows;
- 75 CoRE test rows;
- 58 library rows;
- 11 external rows;
- 160 K GCMC targets;
- 160 K Widom features.

It evaluates:

| Method | Inputs |
|---|---|
| Henry | Henry-law estimate |
| GBM | six structural/global descriptors |
| GBM+W | descriptors plus `logkH`, `qst0` |
| probe | frozen GNN representation |
| probe+W | frozen representation plus Widom features |
| finetune | retrained global MLP and target head |
| finetune+W | fine-tuned head plus Widom features |

Expected output files:

```text
$WORK/train_160_results.csv
$WORK/train_160_doe.csv
$WORK/train_160_test_predictions.csv
$WORK/model_repo/models/finetune_160_finetuneW_ensemble.pth
```

The checkpoint is copied to the repository model directory:

```text
model_repo/models/finetune_160_finetuneW_ensemble.pth
```

The checkpoint contains:

- format/version identifier;
- target definition;
- structural global-feature names;
- Widom feature names;
- target mean and standard deviation;
- Widom means and standard deviations;
- training-MOF names;
- four base GNN state dictionaries;
- four fine-tuned global-MLP state dictionaries;
- four fine-tuned prediction-head state dictionaries.

Verify it:

```bash
python - <<'PY'
import torch
p = "model_repo/models/finetune_160_finetuneW_ensemble.pth"
c = torch.load(p, map_location="cpu", weights_only=False)
print(c["format"])
print(c["target"])
print("ensemble members:", len(c["seeds"]))
print("training structures:", len(c["train_names"]))
print("Widom features:", c["widom_features"])
PY
```

The final packaged run produced approximately:

| Model | CoRE test MAE | External MAE |
|---|---:|---:|
| finetune+W | 0.155 g/L | 0.054 g/L |

These values are reference results, not guaranteed exact values for a new
stochastic simulation or a different software environment.

### Standalone checkpoint inference

After training, later predictions do not require rerunning `train_160.py`.
The reusable inference script is:

```bash
python src/predict_160_checkpoint.py \
  /path/to/feature.pkl \
  --logkH -5.2 \
  --qst0 8.5 \
  --output prediction_160k.csv
```

For a batch of feature pickles, provide a Widom table:

```text
name,logkH,qst0
MOF_A,-5.2,8.5
MOF_B,-4.8,7.9
```

Then run:

```bash
python src/predict_160_checkpoint.py \
  /path/to/MOF_A.pkl /path/to/MOF_B.pkl \
  --widom-csv widom.csv \
  --output predictions_160k.csv
```

The feature pickles must contain the same graph and global descriptor fields
described in Section 9. The script applies the checkpoint's stored Widom
normalization and reports `uptake_160K_5bar_gL` plus `ensemble_std_gL`.
This standalone script uses the saved `finetune+W` model; candidates without
160 K Widom features should use the existing structure-only screening workflow
instead.

## 11. Screening CoRE or new MOFs

### 11.1 Existing CoRE screening set

For the packaged CoRE screening set:

```bash
cd "$WORK"
python screen_featurise.py
python screen_predict.py
```

The structure-only pass predicts the 160 K term using framework features only.
Its output is:

```text
$WORK/screen_core2019.csv
```

After Widom calculations have been run for shortlisted candidates:

```bash
python screen_predict.py refine
```

The refined output is:

```text
$WORK/screen_core2019_refined.csv
```

The important result columns are:

```text
gnn77_y2             77 K / 2 bar prediction
gnn77_y100           77 K / 100 bar prediction
gnn77_dc             77 K isothermal deliverable capacity
p160                 160 K / 5 bar prediction
doe_dc               predicted DOE swing
gnn77_y100_std       77 K ensemble spread
p160_std             160 K ensemble spread
p160_source          structure-only or GAT + Widom
in_domain            applicability-domain flag
```

Rank candidates by:

```text
doe_dc descending
```

Then filter or annotate by:

- `in_domain == True`;
- acceptable `gnn77_y100_std`;
- acceptable `p160_std`;
- no unseen critical elements;
- physically plausible density and void fraction;
- reasonable LCD and PLD;
- no suspected input/structure errors.

### 11.2 Screening a new CIF collection

For new MOFs:

1. Copy CIF files into the RASPA structure directory.
2. Create a candidate table following `data/screen_list.csv`.
3. Run the same graph and Zeo++ featurization.
4. Store one successful feature pickle per candidate under `screen_cache/`.
5. Run structure-only screening.
6. Select a shortlist.
7. Run 160 K Widom simulations for the shortlist.
8. Run `screen_predict.py refine`.
9. Validate the highest-ranked candidates with 160 K / 5 bar and 77 K / 100 bar
   GCMC.

The structure-only pass is intended for broad ranking. The Widom-refined pass is
the recommended final ranking before expensive GCMC.

## 14. Troubleshooting

### Setup stops at queue generation

Cause: pandas is not installed. Install pandas and run:

```bash
python -m pip install pandas
python "$WORK/build_queues.py"
```

The RASPA build may already have completed successfully.

### `core_cache` does not exist

Create it before running the original script:

```bash
mkdir -p "$WORK/core_cache"
python "$WORK/featurise_core.py"
```

### Zeo++ takes a long time

This is expected. Zeo++ computes several geometric descriptors per structure.
Use completed caches, avoid repeating successful structures, and use only as many
workers as available memory supports.

### Missing raw simulation output

Restore the relevant paths from `reference/reference_runs.tgz`, or rerun the
matching queue line with `rq_any.sh`.

### Model checkpoint cannot load

Confirm that:

- PyTorch is installed;
- the checkpoint was copied completely;
- `weights_only=False` is used for this metadata-rich checkpoint;
- the same `MOFNet` architecture is available;
- graph features use the same seven-dimensional atom features and edge distances.

### Predictions are implausible

Check:

- units are g/L, not wt%;
- the candidate is inside the applicability domain;
- `logkH` is computed as `log10(kH)`;
- Widom features use the same 160 K convention;
- the same `UFF_FHm2` convention was used for labels;
- the correct 77 K model ensemble is used for the high-pressure term.

## 16. Recommended end-to-end order

For a fresh reproduction:

```bash
# 1. Environment
export WORK="$PWD/work"
bash setup_env.sh

# 2. Validate one simulation
TEMP=160 FF=UFF_FHm2 bash src/run_fh.sh \
  C19_BADJIC_clean 5 1000 1000 "4 1 3" \
  "$WORK/verify_C19_BADJIC_160_5"

# 3. Restore or generate simulation labels
tar -xzf reference/reference_runs.tgz -C "$WORK" \
  --wildcards 'runs_160/*/Output/System_0/*.data' \
             'runs_w160/*/Output/System_0/*.data' \
             'runs_m2/*/Output/System_0/*.data'

# 4. Generate real-MOF feature caches
mkdir -p "$WORK/core_cache" "$WORK/real_cache"
python "$WORK/featurise_core.py"
python "$WORK/featurise_real.py"

# 5. Train and save the 160 K transfer ensemble
python "$WORK/train_160.py"

# 6. Featurize and screen CoRE candidates
python "$WORK/screen_featurise.py"
python "$WORK/screen_predict.py"

# 7. Run Widom for shortlisted candidates, then refine
python "$WORK/screen_predict.py" refine

# 8. Validate top candidates with RASPA GCMC
bash "$WORK/rq_any.sh" "$WORK/queues/05_core2019_160K.txt" 11
```

The final scientific conclusion should always be based on the combination of:

1. model prediction;
2. ensemble uncertainty;
3. applicability-domain checks;
4. independent RASPA validation;
5. experimental feasibility.
